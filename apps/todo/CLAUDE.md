# apps/todo

## Purpose

One Go binary with three modes. Bare `todo` prints usage, `todo <verb>` acts and exits, and `todo api` serves the JSON `apps/web` reads and the compiled client's files beside it. Three bounded contexts — Tracking, Scheduling, Change History — live in this one artifact. `docs/adrs/0001-ship-todo-as-one-go-binary.md` records why; it is superseded by `docs/adrs/0003-replace-the-tui-with-a-browser-client.md`, which replaced the TUI and `todo serve` with a browser client over a JSON API this binary serves. Everything about the store survived that change untouched. The person's surface is `apps/web` now, and this binary serves it.

## Ownership

- `src/cmd/todo/` — `package main`, nothing but the call into `cli`. It sits under `cmd/` because `scripts/package` names the artifact after the main package's import path, and a main at `src/` would build `src-linux-amd64`.
- `src/cli/` — mode dispatch and the verbs. `ModeOf` decides which mode an invocation asked for; `Run` takes its streams as arguments so every mode is testable without a process.
- `src/store/` — SQLite and the whole write path. Nothing else opens a database.
- `src/schedule/` — Scheduling's rule arithmetic: parsing a recurrence rule, writing it back, and the dates it produces. It opens no database and knows nothing about a Task.
- `src/ai/` — the broker client: an OpenAI-compatible HTTP call out to `inference-runtime-broker`. It opens no database, holds no conversation between calls, and knows nothing about a Lease.
- `src/write/` — the shape a write to a Task takes, Tracking's and Scheduling's alike, the reading of text into `store.Attributes`, and the bridge between the store and `src/ai`: what the Broker is shown of the tracker, and what it said read back. `write.BriefOf` is the one read here, and it is there because it is what the Broker is shown of one Task. `src/cli/` and `src/api/` both call it. It enforces nothing the store does not.
- `src/api/` — `todo api`: routing, JSON encoding, and the status an error takes. It opens no database of its own and serves the compiled client's files when given a directory of them. It holds no rules bar one: `GET /api/files` reads a directory rather than the store, so the root it will not look above is enforced here because there is nowhere else it could be.
- `deploy/systemd/` — the service that starts `todo api` on boot. One file, `todo-api.service`, installed into the operator's `systemd --user` and enabled there. `.unit.json` declares `ships: executable`, so packaging builds the binary; this is what runs it.

## Local Contracts

- **A verb and a request make the same in-process call.** The CLI won its place by implementing the standing obligations in exactly one place; a second path through the rules would give an Agent and a person different contracts.
- **There is one write path, and it is `src/write`.** Take the tree's Lease, do every part of the write inside it, release it: `write.Add` and `write.Edit` are where that sequence lives, and a verb or a handler that repeated it would be the second path through the rules the bullet above rules out. The reading of a date, a duration or a level out of text is there too, as `write.Given`, because a flag set and a JSON body say the same two things: which attributes were given, and their text. An attribute absent leaves it alone where one given empty clears it. `write.FromCapture` is the one reading of what the Broker said, and it drops a value it cannot read rather than refusing the Task.
- **Which verb makes which write is `write.Lifecycle`, and there is one list of the four.** Complete, decline, reopen and delete are named there with the Lease around each, and it returns the whole guarded sequence; `todo <verb>` and `POST /api/tasks/{id}/{verb}` both call it, so neither surface keeps a copy of which four there are nor of the guard. A verb neither recognises comes back as not found rather than as an error of `write`'s own, because the sentence a person at a terminal reads is not the one a JSON client is answered with. `write.LifecycleVerbs` is that sentence's list.
- **A handler is another caller of that same call, and validates nothing the store does not.** `GET /api/files` is the one route this does not reach, because it calls no store; it is the exception the bullet on it below states, and adding a second one is what that bullet exists to make difficult. `src/api/` encodes and routes; a rule enforced in a handler is a rule an Agent running a verb never gets. An unknown `sort` is not checked before the read: `store.Tasks` is what refuses it and what phrases the refusal, and the handler reads `store.Sorts` only to know that a refusal it just got was the caller asking wrongly rather than something failing. So the browser and the terminal say the same sentence about the same mistake, and neither keeps a second copy of it. `api.checked` is where that reading happens and every route narrowed by the query string goes through it, so a bad sort is `400` on a question about the list as well as on the list itself rather than `400` on one and `500` on the other. It refuses through `store.Query.Check`, which is what `store.Tasks` refuses for, worked out without reading: a route that may answer from a cache has to refuse before it does so, and `GET /api/state` calls it above the ETag block for that reason. `If-None-Match: *` matches any representation at all, so without it a caller is told nothing changed about a view the store would never have served.
- **What the Broker is shown is gathered in one place, `write.Gather` and `write.Briefs`.** A dump carries today's date, because `src/ai` reads no clock, and the List and Tag names it may choose from, because an id means nothing to it; `Dump.Filed` matches a name it chose back to the id a write takes, and drops one it invented. A Brief is a Task in the Broker's terms and carries no id. Which of its answers is which attribute is written once too: `write.FromCapture` reads them and drops what it cannot, `write.AsSaid` keeps every one as the words it wrote, `write.AsProposed` does the same for a proposal, and a surface picks whichever its caller can correct. `ai.Patience` is how long one turn is given, and it is the caller's clock in both surfaces.
- **`POST /api/capture` and `POST /api/ask` write nothing.** Neither takes a Lease and neither appends: capture answers in the shape `POST /api/tasks` takes, so the client fills the add sheet with it and submitting is the only thing that writes, and a dump read and then abandoned leaves nothing behind. Capture answers the attributes as the Broker said them rather than parsed. A value it wrote in a way this program cannot read belongs in the field for a person to correct; dropping it is `write.FromCapture`'s rule, and `todo capture` follows that one because it has nobody left to ask. Which Tasks a question is about is the query string, read the way `GET /api/state` reads it.
- **Every write through `todo api` is attributed to whoever started the listener.** There is no authentication and so nobody to name per request: `runAPI` resolves `Options.Actor` once with the same `actor()` the verbs use, so a person at the terminal and the same person in the browser are one Actor in the Change History.
- **A body naming a field the route does not know is refused.** `api.decode` sets `DisallowUnknownFields`, because a client with a typo in an attribute name would otherwise be told its write went through with that attribute quietly dropped. It caps a body at `api.maxBody`, and every attribute in `api.taskBody` is a pointer so that absent and empty stay the two different things `write.Given` makes them.
- **The API's status codes are the CLI's exit statuses.** `200`/`201` for done, `400` for usage, `409` for a refusal (`store.ErrRefused`, `store.ErrHeld`), `500` for a failure, with the body `{"error": "<the sentence the CLI would print>"}`. `api.fail` is the one place that mapping is written.
- **A Subtask is a route under its parent, and the parent is the path.** `POST /api/tasks/{id}/subtasks` reads the same body `POST /api/tasks` does through the same `written`, so one body is read one way; a body naming a `parent` of its own is the caller asking wrongly rather than a second place a parent can come from. The literal segment beats the `{verb}` wildcard beside it, which is what lets the lifecycle route and this one share the prefix.
- **The two history routes answer newest first and drop nothing.** `GET /api/tasks/{id}/history` is `store.HistoryOf` reversed and `GET /api/history` is `store.LatestHistory`, which the store reads in that order already. Both carry the Lease bookkeeping: which kinds are worth drawing is the surface's question, and a route that filtered would decide it for every surface at once. `?limit=` defaults to a page and is capped; one that does not read as a number at least one is a usage error, because a client asking for none of the history meant something else.
- **Scheduling's writes are `write.Repeat`, `write.Unrepeat`, `write.Mark` and `write.DetachEdited`, and there is one list of the three marks.** Tick, skip and detach are named in `write.Mark` with the Lease around each, the way `write.Lifecycle` names the four verbs; `todo repeat` registers a flag per name and `POST /api/tasks/{id}/series/{mark}` routes on the same list, so neither surface keeps a copy of which three there are nor of the guard. All three answer an id so one table holds them: detaching names the Task the date became, and the two that leave the Series alone have nothing new to name. `write.MarkNames` is the list an unknown one is turned away with.
- **Lifting a date out corrected is the fourth thing done to a date, and it is not a mark.** `write.DetachEdited` carries a whole Task where the three carry only the date, so it is `POST /api/tasks/{id}/series/edit` rather than a fourth name under `{mark}`, the literal segment beating the wildcard the way the Subtask route beats `{verb}`. It is one store call, so the detach, the corrections and the copy's memberships commit together and a refusal leaves no half-detached date; the surface previews what the date would become and writes nothing until it is submitted, which is what leaves a date backed out of still an Occurrence. The lifted copy is an ordinary Task from the moment it exists, so it is refused without a title at `400` the way `POST /api/tasks` is.
- **A Series is one value under one path.** `GET /api/tasks/{id}/series` answers the rule as the store wrote it back and a page of the dates it produces, computed and never stored; `PUT` sets or replaces the rule, because a Series is edited as one thing rather than a row of columns; `DELETE` takes it off the Task and erases nothing, since the Series and every mark on its dates stay in the record; it is `todo repeat -off`'s route and has no other. A Task carrying no Series answers `repeats: false` rather than `404`: most Tasks do not repeat, and that is not a mistake. A rule the parser cannot read is `400` in the parser's own sentence, and an empty one is too, because stopping is the `DELETE`. `?limit=` defaults to a page and is capped, read through the one `api.page` the history routes read: it is the same question on every route, so it is the same word and the same sentence, which names what is being counted.
- **`POST /api/breakdown` writes nothing and holds no Lease.** It is a turn: the Task as a Brief with everything already answered, and back comes what the Broker still needs to know or what it proposes, in the same `taskBody` shape capture answers in so a proposal is corrected and submitted like a dump read into a Task. Each turn is a request that ends and holds nothing, so an approved proposal is written by `POST /api/tasks/{id}/subtasks` under the Lease that write takes for itself. Which proposals were approved is the client's to remember: two can come back saying the same thing and only the order tells them apart, so position never crosses the wire and what arrives is the bodies of the ones ticked. A turn with neither questions nor proposals is a failure rather than a usage error.
- **`write.BriefOf` reads one Task out of the list rather than by a store call of its own.** It includes every state, because a Task somebody is breaking down may be any of them.
- **`GET /api/state`'s ETag is `WALToken` hashed with the query.** The token is store-global and the response is not, so a client changing a filter or a sort with no write in between would otherwise be answered `304` for a different representation. An empty token means the log could not be stat'd rather than that nothing changed, so the response then carries no ETag at all. It goes on the response that was sent, never on an error body: a tag on a `500` is one a client hands back and is answered `304` for a screen it never received. `api.matches` reads `If-None-Match` as RFC 9110 writes it: several tags to a line, `W/` weak, `*` for any. A tag a proxy joined to another would otherwise re-read the whole list every second.
- **The client's files are served under `/api/`'s feet, not over them.** The fallback answers any path so a reload on one only the browser knows about reaches the client rather than a `404`; `/api/` is registered ahead of it, so a route this package does not serve is a usage error with a sentence in it rather than `index.html` at `200` for the client to fail to parse as JSON. It is registered with or without `-web`, so serving the JSON alone and serving it beside the client say the same thing about the same bad route. One `http.Dir` both decides whether a path names a file and serves it, so the containment check keeping a request inside the directory is the standard library's own rather than a second one written beside it to match.
- **An empty collection is `[]` on the wire, never `null`.** `Tasks`, `Lists`, `Tags` and `Marks` are allocated empty, because a client that must tell `null` from `[]` before it can count is being asked a question the store never asks.
- **`todo api` has no authentication, deliberately, and is meant for the LAN.** That was `todo serve`'s posture minus the public key it wanted; changing it is what ADR 0003's first re-check trigger covers. Meant for, not confined to: nothing in this binary narrows the listener, and the bullet below says what decides its reach.
- **The service unit names no `TODO_DB` and no `TODO_ACTOR`.** Unset, the binary resolves `~/.config/todo/todo.db` and the login name, which is exactly what a verb run at the terminal resolves; naming either in `deploy/systemd/todo-api.service` would give the service a store or an Actor of its own. The Lease is only a Lease while both open the same file, and the browser and the terminal are one Actor in the Change History only while neither is told otherwise. It does name `-web`, which has no default at all, and `-addr`, which has one — `:8080`, restated so the port a host is reached on is read off the service rather than inferred from the binary. `:8080` is a wildcard bind, so what the listener is reachable on is the host's interfaces and not this file.
- **Two artifacts are placed on the deploy host, and nothing enforces they match.** The binary `scripts/package todo` builds goes to `~/.local/bin/todo`, and the files `npm run build` writes to `apps/web/dist/` go to `~/.local/share/todo/web/`. `-web` pointing at a directory that is missing or stale is a client that loads and disagrees with the JSON, not a service that fails to start.
- **Every connection DSN carries `_txlock=immediate`.** `database/sql` issues a deferred `BEGIN`, and the deferred path loses writes under contention. `store.dsn` holds the measurement, and `concurrency_test.go` fails if the flag goes.
- **The Change History is append-only, enforced by trigger.** `UPDATE` and `DELETE` against it `RAISE(ABORT)`. A deletion is an appended entry, never an erasure.
- **The fold runs inside the appending writer's transaction.** Current state and the entry producing it commit together. Nothing sweeps, nothing is awake between invocations, and no reader materializes.
- **A Lease is a row keyed on a top-level Task, and it covers that Task's whole nested tree.** A `BEFORE INSERT` trigger rejects one keyed on a Subtask. A write five levels down needs the root's Lease; that blocking cost is deliberate, and `docs/adrs/0002-subtask-tree-is-one-aggregate.md` is why.
- **A Subtask nests to five levels, never moves, and cannot leave its parent complete.** All three are triggers on `task`, so no surface can offer a re-parent or a sixth level by accident. `depth` is folded from the parent's rather than walked. The completion rule consults direct children only, since an open grandchild keeps its own parent open.
- **A Task ends two ways, and they are not the same answer.** Completing says the work was done; Declining says it will not be. Each is its own entry, its own column and its own `Query` flag, because a tracker that folded one into the other could not tell a person afterwards which happened, and telling them apart is the whole reason for the second one. Neither is a deletion: a deleted Task is one that should not have been there. Reopening undoes either, and one Task Reopened serves both since the Change History already says which state it came out of. It does not undo a deletion: `ReopenTask` reads the row inside the append's own transaction and refuses a deleted Task with `store.ErrGone`, because a Task that should not have been there is not a Task somebody puts aside, and declining is what putting one aside is for. Answering 200 and leaving the row deleted — which is what this did before — wrote a reopening into an append-only record that did not happen. `store.Refused` is the one list of which errors are the store turning a write away, so the API's 409 and the CLI's exit 3 cannot come to disagree about what a refusal is. A Task ends once: `a_task_ends_once` refuses the second ending rather than letting it overwrite the first, so correcting yourself is a reopen and then the other ending, and the Change History reads that way.
- **Completing and declining refuse over an open child; reopening one and adding one cascade instead.** A child is open until it reaches one of the two terminal states, so a declined child no more holds its parent open than a completed one does. Completing and declining are the directions a person drives, so they are the directions that say no. The other two cannot refuse without stranding the person, so each reopens every ended Task above it, clearing both columns. Both walks are a `WITH RECURSIVE ancestry` inside one `UPDATE`: `recursive_triggers` is off by default, so a trigger firing a trigger reaches exactly one level and silently stops. Both leave no entry per reopened ancestor: the entry that caused the cascade is there and the cascade is a rule of the store rather than an act of an Actor, so a replay of the Change History reproduces the ancestors' state only by re-running the same rule.
- **A Task out of sight takes its subtree with it.** Every narrowing a read applies — deleted, completed, declined, snoozed and the List — goes inside both arms of the `depth_first` walk, not in the outer `WHERE`, so a subtree is reachable only through a visible root. Filtering per row instead leaves children on the screen under a parent that is gone.
- **A Tag narrows a read the way a List does, and a read narrows to any of several.** `Query.Tags` is a set of ids and an `EXISTS` against `task_tag`, the shape `Query.List` is against `task_list`, because a Task belongs to the two the same way and only means something different by it. A Task carrying any one of the named Tags is in the read: naming a second is widening what is asked for, and an intersection would answer nothing on the second. The ids travel as one JSON array argument read back with `json_each`, so the query's positional arguments stay the shape it is written against however many are named. Both surfaces reach it, neither weaker: `todo list -tag <id>` repeated and `GET /api/state?tag=<id>` repeated.
- **Search is the one narrowing that reaches upward.** `Query.Search` matches a Task on its own Title, Description or Why, and the Tasks above a match come back with it unmatched, so the match has somewhere to sit and the answer is still a tree: a Subtask called "paint" under a Task called "redecorate" is otherwise unfindable by the word somebody would type. The narrowings a caller set deliberately still apply to every row, so a match under a Task those hide stays hidden. The comparison is `instr(lower(x), lower(?)) > 0` rather than `LIKE`: somebody searching for `50%` means the characters, and `LIKE` would read them as a wildcard unless every search were escaped on the way in. It is case-insensitive over ASCII, which is `lower()`'s reach without an extension, and it is a substring rather than a word.
- **`store.Sorts` is the one list of sorts there is**, in the order `docs/features.md` names them. The error a bad `-sort` gets, the flag help a person reads, the sorts `GET /api/state` accepts and the `sorts` it answers with all come from it, so none of them can name a set the store does not have. Serving the list is what stops a surface keeping its own copy and offering a sort the store would refuse.
- **A List and a Tag are aggregates of their own, and a Task carries the id rather than the text.** Each exists before any Task carries it and outlives the last one that did, so a rename or a recolor is one append however many Tasks show it. A Tag's frequency is counted at read time, never stored.
- **Creating or renaming a List or a Tag takes no Lease; carrying one does.** A Lease covers a top-level Task and its tree, and a List is in nobody's tree. Membership is a write to the Task, so it goes through the same guard as any other.
- **Deleting a List or a Tag keeps every Task that carried it.** `DeleteList` and `DeleteTag` append one `task_unlisted` or `tag_detached` per Task and then the `list_deleted` or `tag_deleted` that folds the row away, all in one transaction, so a Task's history says it left the collection rather than falling silent. `store.remove` is the one write touching Tasks without a Lease: a List spans trees, so no single Lease covers this and one per tree would mean a List could not be deleted while anybody held a Task that carried it. What it appends takes nothing off a Task but a membership. An id naming nothing is refused before anything is appended, because an entry deleting a List that never existed is one no later write can take back and a surface reporting a typo as done would leave the person believing it. `store.collection` is the one statement of which of the two is being deleted, so the tables, the column and the two kinds cannot be passed in the wrong order. Both surfaces reach it: `todo lists delete <id>` and `todo tags delete <id>`, and `DELETE /api/lists/{id}` and `DELETE /api/tags/{id}`.
- **A sort orders siblings and never flattens the tree.** `Query.Sort` substitutes the key into the depth-first path, so roots and children both come back in the asked-for order. A Task with no deadline sorts after every Task that has one.
- **`Tasks` comes back depth first**, a parent followed by everything under it before the next root, so a surface indents by `Depth` rather than rebuilding the tree.
- **The guard sits on the append, not on the folded row.** The fold is a trigger on the append, so guarding the append guards every write exactly once and makes an unleased entry unrepresentable. The predicate walks to the root and then looks the Lease up by primary key; joining `lease` against the walk re-runs the recursion per row and costs ten times as much.
- **Leases are symmetric.** Nothing in the API names a holder or tells a person's Lease from an Agent's. `ErrHeld` says a Lease is held and no more.
- **Expiry is the clause `expires_at > now`, never a sweep.** No reader deletes a stale Lease row. Taking over a stale one appends Lease Broken, so a crashed run leaves a trail; there is no Lease Expired.
- **Instants are stored in the fixed-width `stamp` format, not `time.RFC3339Nano`.** RFC3339Nano trims trailing zeros from the fraction, which puts `12:00:00.5Z` before `12:00:00Z` under SQLite's TEXT comparison. `expires_at > now` and `deadline < now` both depend on lexicographic order being chronological order.
- **Reads write nothing.** Overdue is `deadline < now`, a stale Lease is a clause in a predicate, and an Occurrence is computed from its Series. A read that appends anything is a defect with a test against it.
- **Every write carries an Actor; reads are not attributed.** `TODO_ACTOR` names an Agent, and a person falls back to their login. An Agent names itself `<harness>/<model>`, so a history log can say that Opus wrote this and Fable wrote that, and which agent each was acting as. The store neither parses nor validates it: the column is `TEXT` and anything is a legal Actor, because the alternative is a write refused over its own name. A surface splits on the first slash for display and shows what it was given whenever there is none, which is every entry appended before the convention existed.
- **A writing verb takes the Lease covering its target's tree, writes, and gives it back.** A verb acts and exits, so it holds `store.WriteTTL` and never strands a tree behind a dead process. `store.WriteTTL` is the span every surface writes under, so no surface names its own; the breakdown's think-time Lease is the one named exception, below.
- **What a read worked out about a Task is `Task.Marks`.** Overdue, done, declined, deleted and snoozed are decided once in the store and said in the same words everywhere, so a Task cannot read as snoozed from a keyboard and plain on a screen. A surface decides only how to draw them.
- **A column added or renamed after the first release is asked for by name.** `CREATE TABLE IF NOT EXISTS` leaves an existing table as it is and SQLite has no `ADD COLUMN IF NOT EXISTS`, so `addDeclinedAt` and `renameColour` read `pragma_table_info` and alter. Both run inside the schema's own transaction and before the schema, so the trigger bodies reading the column are created after it exists on a store of either age. A rename also needs the folds that read the column to be `DROP` and `CREATE` rather than `IF NOT EXISTS`: SQLite rewrites an existing trigger's body to the new column name but not the payload key it reads, so a stale fold would quietly stop seeing the attribute. The six color folds are pairs for that reason. Entries already in the Change History keep whichever key they were appended with; nothing re-reads them.
- **`Open` retries a busy schema apply.** Turning the write-ahead log on is a `journal_mode` change taking the exclusive lock, and SQLite runs no busy handler for one, so `busy_timeout` cannot cover it: several processes opening a store that does not exist yet leave all but one with `SQLITE_BUSY`. The loser waits only for the winner's switch, so `Open` backs off linearly a few times. Every open after the first finds the log on and the switch a no-op.
- **`Open` applies the schema in one transaction.** Several triggers are a `DROP` followed by a `CREATE`, so an older store gets the current definition; applied without the write lock, two processes opening one store at once interleave those pairs and one fails on a trigger the other has just made.
- **An edit says what it touches and nothing else.** An attribute flag nobody typed leaves its attribute alone; one given empty clears it. The fold reads `json_type(payload, '$.x') IS NULL` for untouched and a JSON null for cleared, which is the distinction `COALESCE` cannot express, and `fs.Visit` is what makes the CLI say it.
- **The lifecycle verbs are one shape.** `complete`, `decline`, `reopen` and `delete` each take one id, no flags, and the same guard, so the dispatch and the CLI's map of them are the only places a new one is named.
- **Exit status is 0 for done, 1 for a failure, 2 for usage, 3 for a refusal.** A refusal is the store turning a write away — no Lease, or one another Actor holds — and a surface distinguishes it from a crash. A bad attribute value is refused where it was typed, so `store.ParseLevel` is the CLI's, not only the write path's.
- **The two attachment routes are one path and differ by method.** `POST` and `DELETE /api/tasks/{id}/attachments` both carry the target in the body, because a pointer is a file path or a web address and carries its own slashes, which a path segment cannot hold without being escaped into something unreadable in a log. The `POST` beats the `{verb}` wildcard beside it on the literal segment, the way the Subtask route does; the `DELETE` has no wildcard to beat, since no lifecycle verb is one. Both go through `write.Attach` and `write.Detach`, which take the Task's Lease, since pointing a Task at something is a write to the Task and a handler wrapping the Lease itself would be the second write path. What counts as somewhere to point is `store.pointer`'s alone. A target with nothing in it is the one thing the handler answers before the store does: it restates the store's sentence to get `400` rather than the `500` a plain store error falls through to, which is the mapping `editTask` makes for a Title sent empty, and `attachments_test.go` asks the store for that sentence rather than repeating it so the two cannot drift apart.
- **`GET /api/files` lists one directory of the machine this listener runs on, and opens nothing.** It is the one route reading anything outside the store, and it is there because a pointer naming a file names it on this machine: a browser's own file input answers with a bare filename and no directory, so a file chosen on a phone would be a path nothing here could resolve. The root is the home directory of whoever started the listener, and there is no flag for it: `Options.Browse` is the seam a test roots the route somewhere of its own through, not a knob an operator turns, and it stays that until somebody asks for the other thing. `within` judges a path twice, on how it is spelled and then on where it lands, so a link out of the root is refused the same way `..` is and a directory honestly called `..foo` is not. The spelling is judged first so a path outside the root is refused before the machine is touched: resolving it first and reporting what that said would answer whether an arbitrary absolute path exists to anybody who can reach the route. Everything outside gets the one sentence, there or not; inside, why a path cannot be listed is said plainly, since that is a directory the caller could have listed anyway. Nothing is hidden, because a dotfile left out is a picker that cannot reach a config directory. It lists and never opens: a route serving a file's contents would be the tracker holding the copy the bullet below says it never holds. Its own root rather than the LAN is what bounds it, decided at issue #60: the listener is meant for the LAN and not confined to it, and a directory listing of somebody's home directory is worth a bound of its own whatever the network is. `rooted` resolves the root through the symlinks `within` resolves a path through, so the two sides of that comparison are the same kind of path and a listener pointed at a link lists what it points at.
- **An Attachment is a pointer, and the tracker never holds a copy.** A file path or a web address, written down and nothing more: a path is resolved to an absolute one against the directory the process doing the resolving runs in, an address is kept as typed, and nothing is fetched. `todo attach` at a terminal resolves against the shell's directory; `todo api` resolves against the service's, which `deploy/systemd/todo-api.service` names no `WorkingDirectory` for, so a relative path typed in a browser is not the one the same text would mean at a prompt. A target that moves leaves a dead link the tracker cannot tell you about, decided at issue #3, so there is no checker and never will be.
- **Deleting a Task collects nothing.** Nothing was copied in, so there is nothing to collect. The pointers stay on the deleted Task and what they name is untouched.
- **A Series is a rule and nothing else.** Scheduling's two tables hold ids, a rule, a date and a state; no title, description or estimate crosses into it, and `TestNoTaskContentEntersScheduling` reads both tables to check. Tracking points at the rule through `task.series_id`.
- **A rule is written the way it is said, and `schedule.Parse` is the only reader of one.** The units are day, week, month and year, each as `daily`/`weekly`/`monthly`/`yearly` or `every [N] <unit>s`. `on` runs to the next keyword rather than taking one word: a weekly rule names days (`on mon,thu`), a monthly one names either a day of the month (`on 15`) or a weekday counted inside it (`on the third tue`, `on the last fri`, `on the last day`). `Rule.Nth` carries that count with `schedule.Last` for the last one. The counts stop at a fourth, which every month has: a fifth weekday is in some months and not others, so a rule counting one could produce nothing at all and `Next` could not tell that from a rule that has run out. The last one is what a person meant anyway. A yearly rule takes no `on` and steps by twelves of months, so an anchor on the 29th of February clamps to the 28th rather than sliding into March. `String` writes every form back exactly as Parse reads it, because a Series is stored as that text.
- **An Occurrence is computed on every look.** There is no row for a date until somebody ticks, skips or Detaches it, and then it is keyed by (series, date). A reader that shows next year's dates appends nothing and stores nothing.
- **Detaching one date lifts it out into an ordinary Task.** The copy carries the recurring Task's content, deadlined on that date and repeating on nothing, and the rule stops producing the date. Later edits to the rule do not reach it, which is the point of detaching rather than editing the Series.
- **A mark is an ordinary guarded write; changing the rule is too.** Each takes the Lease covering the Task's tree. Creating a Series and pointing the Task at it are one transaction, so a refusal leaves no Series behind.
- **Nothing in Scheduling runs on a schedule.** No sweep materializes dates and nothing is awake to notice one arriving; `src/schedule` says so in its package comment.
- **A level is served with the example that says what it means.** `store.Levels` is the three and `store.PriorityExamples` and `store.ImpactExamples` are what each means, which differ: high priority is today, high impact is what unblocks other work. `store.PriorityOffers` and `store.ImpactOffers` pair each map with the three in order and `GET /api/state` answers `priorities` and `impacts` from them; they take no argument for the reason `store.ColorNames` does not, so neither can be handed a map missing a level. The examples are why they are served rather than left to each surface: they are what makes the three words mean the same thing to a person and to an Agent, and a surface keeping the words alone keeps none of it. `store.LevelNames` is the other reading and everything naming the three is written from it: `write.LevelLabels` for the CLI's `-priority` and `-impact` help, which names the three and not their examples because three sentences is a wall in a flag, and both refusals in `attributes.go`, so a fourth added to `store.Levels` cannot be left out of the sentence that lists them. An Agent with room for the examples reads them off the route.
- **A color is one of nine, named, and refused anywhere else.** `store.Colors` is the list and `checkColor` gates every write carrying one: a Task's attributes, and a List's or a Tag's creation and rename. `store.ColorNames` is the one reading of it every surface offers from: the CLI's `-color` help, and the `colors` `GET /api/state` answers with. `store.SnoozeNames` is the same for the four offered snoozes, which are not all a snooze can be — `write.Snooze` reads a plain duration too — so what the route serves is the offer and not the rule. Both are served for the reason `sorts` is: a surface keeping its own list offers a tenth color the day one is added here and not there.
- **`store.Detached` is the one statement of what a detached copy carries.** The append that writes it reads that function, and `POST /api/tasks/{id}/series/edit` hands the whole copy back, so a surface previewing one draws what the write produces rather than a second guess at it. `store.day` builds in `time.Local`, so a detached deadline is the same midnight every other deadline for that day is.
- **Bare `todo` is usage, exit 2.** It opened the TUI until the browser client replaced that surface, and it is an error rather than a help screen because nothing was asked for. An Agent that runs `todo` by accident gets a sentence naming the verbs and `todo api`, not a hung process. `cli.verbs` is the one list of the verbs there is: the dispatch looks a verb up in it and the usage sentence is written from it, so the binary cannot offer one it does not take. A mode `ModeOf` returns that `Run` has no case for prints usage too, because exiting 0 having done nothing is the one answer that would go unnoticed.
- **The AI is an outbound HTTP call, never embedded inference.** `inference-runtime-broker` at `10.10.10.13:4010` already runs and is the only thing that infers; `TODO_AI_URL` and `TODO_AI_MODEL` point elsewhere, and with no model named the broker is asked which one it can chat with. That answer is settled once behind a mutex and kept apart from the caller's `Model` field, because a breakdown and an ask can be in flight together. A 429 is its memory budget, so it is reported as a wait with a number of seconds rather than as a fault.
- **A breakdown leaves nothing durable unless it is approved.** A turn answers proposals and stores none: they are shown, ticked or unticked, and gone when whoever asked stops asking. Only submitting writes, and it writes only what is still ticked. There is no Assistance aggregate, no table and no artifact, which is what issue #4 settled.
- **`?` is a read.** The question goes with the Tasks in view, because the broker holds nothing between calls, and no Lease is taken. There is no breakdown verb: approval gates each step, and a verb that acts and exits has nobody to ask.
- **`POST /api/capture` writes nothing and takes no Lease.** The form it fills is the gate, so a dump that is read and then thought better of leaves nothing behind, the same as a proposal nobody ticks. `todo capture` is the one way past that gate, for the reason its own bullet gives.
- **A dump amending a Task carries the Task as it stands and comes back whole.** The broker answers with the Task as it should end up, not a difference, because nothing on this side could apply a difference to attributes it was not shown. An answer left empty leaves what was there.
- **What the broker fills in is dropped rather than refused when it cannot be read.** A date, a duration or a level written in a way this program cannot parse is left out of the draft, and a List or Tag name that is not one of the offered ones is dropped rather than created. A name goes out and an id comes back, so the store's rule that a Task carries the id holds through the broker.
- **`todo capture` is the one verb that writes what the broker said, and `-dry` is why it can.** A dump is a person's own words about a Task they are describing, not a proposal of work nobody asked for, so there is nobody left to ask; `-dry` prints what was read and writes nothing, which is where it is checked before it is taken at its word. The Task is written first and its List and Tag membership second under the Task's own Lease, so a refusal there leaves it filed under nothing rather than not written.
- **`TODO_DB` overrides the store path**, which is how a test and an Agent run against a store of their own. The default sits under the user config directory.

## Work Guidance

- Tests first, at the seams the domain already draws: append-only, purity of reads, the Lease predicate, gaplessness under contention.
- Concurrency claims are asserted against real OS processes, not goroutines. Goroutines share one `*sql.DB` and one pool, so they never reach the file lock the defect hides behind. `TestMain` re-executes the test binary as the child.
- The broker is shared and its chat model is large: a 429 saying `scheduler_busy` means the GPU budget is spoken for, not that anything here is wrong. Tests stand a broker in with `httptest` and never reach the LAN.
- `todo capture` is the dump: words after it are read into one Task, and `-dry` prints what was read without writing.
- `todo attach` is the pointers: bare with an id it lists them, a target adds one, and `-off` takes one off.
- `todo repeat` is the one verb that reaches Scheduling: bare it shows the rule and the next dates, words after the id set the rule, and `-tick`, `-skip`, `-detach` and `-off` are the rest.
- The store's exported vocabulary is `CONTEXT.md`'s: Task, Subtask, List, Tag, Lease, Attachment, Series, Occurrence, Actor.
- A Task's attributes are the set `docs/features.md` asks for and no more: title, description, why, creation date, deadline, estimate, priority, impact, snooze, color, and any number of key/value pairs. Priority and impact are the same three levels, each carrying an example in `PriorityExamples` and `ImpactExamples`. The four offered snoozes are 1 hour, 1 day, 1 week, 1 month, and the month one clamps to the target month's last day.

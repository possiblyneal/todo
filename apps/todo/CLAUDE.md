# apps/todo

## Purpose

One Go binary with four modes. Bare `todo` opens the TUI, `todo <verb>` acts and exits, `todo serve` serves the same TUI over SSH on the LAN, and `todo api` serves the JSON `apps/web` reads and the compiled client's files beside it. Three bounded contexts — Tracking, Scheduling, Change History — live in this one artifact. `docs/adrs/0001-ship-todo-as-one-go-binary.md` records why; it is superseded by `docs/adrs/0003-replace-the-tui-with-a-browser-client.md`, which replaces the TUI and `todo serve` with a browser client over a JSON API this binary serves. Everything about the store survives that change untouched. Until `docs/plans/browser-client.md` reaches its deletion stage the TUI and serve contracts below are binding, because the TUI stays the working surface until the browser is one.

## Ownership

- `src/cmd/todo/` — `package main`, nothing but the call into `cli`. It sits under `cmd/` because `scripts/package` names the artifact after the main package's import path, and a main at `src/` would build `src-linux-amd64`.
- `src/cli/` — mode dispatch and the verbs. `ModeOf` decides which mode an invocation asked for; `Run` takes its streams as arguments so every mode is testable without a process.
- `src/store/` — SQLite and the whole write path. Nothing else opens a database.
- `src/schedule/` — Scheduling's rule arithmetic: parsing a recurrence rule, writing it back, and the dates it produces. It opens no database and knows nothing about a Task.
- `src/ai/` — the broker client: an OpenAI-compatible HTTP call out to `inference-runtime-broker`. It opens no database, holds no conversation between calls, and knows nothing about a Lease.
- `src/write/` — the shape a write to a Task takes, the reading of text into `store.Attributes`, and the bridge between the store and `src/ai`: what the Broker is shown of the tracker, and what it said read back. `src/cli/` and `src/api/` both call it; `src/tui/` still holds its own copy of the sequence in `src/tui/write.go` and its own briefs, and the browser client plan deletes that surface rather than moving it. It enforces nothing the store does not.
- `src/api/` — `todo api`: routing, JSON encoding, and the status an error takes. It holds no rules, opens no database of its own, and serves the compiled client's files when given a directory of them.
- `src/serve/` — `todo serve`: the SSH front door, built on `charm.land/wish/v2`. It builds a `tui.Model` per connection and owns nothing else; no rule and no store call lives here.
- `src/tui/` — the main view, the add and edit screens, and the screens the verb keys open, built on `charm.land/bubbletea/v2` and `charm.land/huh/v2`. It writes through the same store calls the verbs use.

## Local Contracts

- **A verb and the TUI make the same in-process call.** The CLI won its place by implementing the standing obligations in exactly one place; a second path through the rules would give an Agent and a person different contracts.
- **There is one write path, and it is `src/write`.** Take the tree's Lease, do every part of the write inside it, release it: `write.Add` and `write.Edit` are where that sequence lives, and a verb or a handler that repeated it would be the second path through the rules the bullet above rules out. The TUI is the one surface still writing its own, and it goes when the surface does. The reading of a date, a duration or a level out of text is there too, as `write.Given`, because a flag set and a JSON body say the same two things: which attributes were given, and their text. An attribute absent leaves it alone where one given empty clears it. `write.FromCapture` is the one reading of what the Broker said, and it drops a value it cannot read rather than refusing the Task.
- **A handler is another caller of that same call, and validates nothing the store does not.** `src/api/` encodes and routes; a rule enforced in a handler is a rule an Agent running a verb never gets. An unknown `sort` is not checked before the read: `store.Tasks` is what refuses it and what phrases the refusal, and the handler reads `store.Sorts` only to know that a refusal it just got was the caller asking wrongly rather than something failing. So the browser and the terminal say the same sentence about the same mistake, and neither keeps a second copy of it.
- **What the Broker is shown is gathered in one place, `write.Gather` and `write.Briefs`.** A dump carries today's date, because `src/ai` reads no clock, and the List and Tag names it may choose from, because an id means nothing to it; `Dump.Filed` matches a name it chose back to the id a write takes, and drops one it invented. A Brief is a Task in the Broker's terms and carries no id. Which of its answers is which attribute is written once too: `write.FromCapture` reads them and drops what it cannot, `write.AsSaid` keeps every one as the words it wrote, and a surface picks whichever its caller can correct. `ai.Patience` is how long one turn is given, and it is the caller's clock in both surfaces.
- **`POST /api/capture` and `POST /api/ask` write nothing.** Neither takes a Lease and neither appends: capture answers in the shape `POST /api/tasks` takes, so the client fills the add sheet with it and submitting is the only thing that writes, and a dump read and then abandoned leaves nothing behind. Capture answers the attributes as the Broker said them rather than parsed. A value it wrote in a way this program cannot read belongs in the field for a person to correct; dropping it is `write.FromCapture`'s rule, and `todo capture` follows that one because it has nobody left to ask. Which Tasks a question is about is the query string, read the way `GET /api/state` reads it.
- **Every write through `todo api` is attributed to whoever started the listener.** There is no authentication and so nobody to name per request: `runAPI` resolves `Options.Actor` once with the same `actor()` the verbs use, so a person at the terminal and the same person in the browser are one Actor in the Change History.
- **A body naming a field the route does not know is refused.** `api.decode` sets `DisallowUnknownFields`, because a client with a typo in an attribute name would otherwise be told its write went through with that attribute quietly dropped. It caps a body at `api.maxBody`, and every attribute in `api.taskBody` is a pointer so that absent and empty stay the two different things `write.Given` makes them.
- **The API's status codes are the CLI's exit statuses.** `200`/`201` for done, `400` for usage, `409` for a refusal (`store.ErrRefused`, `store.ErrHeld`), `500` for a failure, with the body `{"error": "<the sentence the CLI would print>"}`. `api.fail` is the one place that mapping is written.
- **`GET /api/state`'s ETag is `WALToken` hashed with the query.** The token is store-global and the response is not, so a client changing a filter or a sort with no write in between would otherwise be answered `304` for a different representation. An empty token means the log could not be stat'd rather than that nothing changed, so the response then carries no ETag at all. It goes on the response that was sent, never on an error body: a tag on a `500` is one a client hands back and is answered `304` for a screen it never received. `api.matches` reads `If-None-Match` as RFC 9110 writes it: several tags to a line, `W/` weak, `*` for any. A tag a proxy joined to another would otherwise re-read the whole list every second.
- **The client's files are served under `/api/`'s feet, not over them.** The fallback answers any path so a reload on one only the browser knows about reaches the client rather than a `404`; `/api/` is registered ahead of it, so a route this package does not serve is a usage error with a sentence in it rather than `index.html` at `200` for the client to fail to parse as JSON. It is registered with or without `-web`, so serving the JSON alone and serving it beside the client say the same thing about the same bad route. One `http.Dir` both decides whether a path names a file and serves it, so the containment check keeping a request inside the directory is the standard library's own rather than a second one written beside it to match.
- **An empty collection is `[]` on the wire, never `null`.** `Tasks`, `Lists`, `Tags` and `Marks` are allocated empty, because a client that must tell `null` from `[]` before it can count is being asked a question the store never asks.
- **`todo api` has no authentication, deliberately, and binds to the LAN.** That is `todo serve`'s posture minus the public key; changing it is what ADR 0003's first re-check trigger covers.
- **Every connection DSN carries `_txlock=immediate`.** `database/sql` issues a deferred `BEGIN`, and the deferred path loses writes under contention. `store.dsn` holds the measurement, and `concurrency_test.go` fails if the flag goes.
- **The Change History is append-only, enforced by trigger.** `UPDATE` and `DELETE` against it `RAISE(ABORT)`. A deletion is an appended entry, never an erasure.
- **The fold runs inside the appending writer's transaction.** Current state and the entry producing it commit together. Nothing sweeps, nothing is awake between invocations, and no reader materializes.
- **A Lease is a row keyed on a top-level Task, and it covers that Task's whole nested tree.** A `BEFORE INSERT` trigger rejects one keyed on a Subtask. A write five levels down needs the root's Lease; that blocking cost is deliberate, and `docs/adrs/0002-subtask-tree-is-one-aggregate.md` is why.
- **A Subtask nests to five levels, never moves, and cannot leave its parent complete.** All three are triggers on `task`, so no surface can offer a re-parent or a sixth level by accident. `depth` is folded from the parent's rather than walked. The completion rule consults direct children only, since an open grandchild keeps its own parent open.
- **A Task ends two ways, and they are not the same answer.** Completing says the work was done; Declining says it will not be. Each is its own entry, its own column and its own `Query` flag, because a tracker that folded one into the other could not tell a person afterwards which happened, and telling them apart is the whole reason for the second one. Neither is a deletion: a deleted Task is one that should not have been there. Reopening undoes either, and one Task Reopened serves both since the Change History already says which state it came out of. A Task ends once: `a_task_ends_once` refuses the second ending rather than letting it overwrite the first, so correcting yourself is a reopen and then the other ending, and the Change History reads that way.
- **Completing and declining refuse over an open child; reopening one and adding one cascade instead.** A child is open until it reaches one of the two terminal states, so a declined child no more holds its parent open than a completed one does. Completing and declining are the directions a person drives, so they are the directions that say no. The other two cannot refuse without stranding the person, so each reopens every ended Task above it, clearing both columns. Both walks are a `WITH RECURSIVE ancestry` inside one `UPDATE`: `recursive_triggers` is off by default, so a trigger firing a trigger reaches exactly one level and silently stops. Both leave no entry per reopened ancestor: the entry that caused the cascade is there and the cascade is a rule of the store rather than an act of an Actor, so a replay of the Change History reproduces the ancestors' state only by re-running the same rule.
- **A Task out of sight takes its subtree with it.** Every narrowing a read applies — deleted, completed, declined, snoozed and the List — goes inside both arms of the `depth_first` walk, not in the outer `WHERE`, so a subtree is reachable only through a visible root. Filtering per row instead leaves children on the screen under a parent that is gone. The rule binds a surface that narrows in Go too: the TUI's Tag filter drops the run of deeper rows under a Task the chosen Tags pass over.
- **`store.Sorts` is the one list of sorts there is**, in the order `docs/features.md` names them. The error a bad `-sort` gets, the flag help a person reads and the order the TUI's sort key cycles in all come from it, so none of them can name a set the store does not have.
- **A List and a Tag are aggregates of their own, and a Task carries the id rather than the text.** Each exists before any Task carries it and outlives the last one that did, so a rename or a recolor is one append however many Tasks show it. A Tag's frequency is counted at read time, never stored.
- **Creating or renaming a List or a Tag takes no Lease; carrying one does.** A Lease covers a top-level Task and its tree, and a List is in nobody's tree. Membership is a write to the Task, so it goes through the same guard as any other.
- **Deleting a List or a Tag keeps every Task that carried it.** `DeleteList` and `DeleteTag` append one `task_unlisted` or `tag_detached` per Task and then the `list_deleted` or `tag_deleted` that folds the row away, all in one transaction, so a Task's history says it left the collection rather than falling silent. `store.remove` is the one write touching Tasks without a Lease: a List spans trees, so no single Lease covers this and one per tree would mean a List could not be deleted while anybody held a Task that carried it. What it appends takes nothing off a Task but a membership. An id naming nothing is refused before anything is appended, because an entry deleting a List that never existed is one no later write can take back and a surface reporting a typo as done would leave the person believing it. `store.collection` is the one statement of which of the two is being deleted, so the tables, the column and the two kinds cannot be passed in the wrong order. Both surfaces reach it: `todo lists delete <id>`, `todo tags delete <id>`, and the TUI's describe popup.
- **A sort orders siblings and never flattens the tree.** `Query.Sort` substitutes the key into the depth-first path, so roots and children both come back in the asked-for order. A Task with no deadline sorts after every Task that has one.
- **`Tasks` comes back depth first**, a parent followed by everything under it before the next root, so a surface indents by `Depth` rather than rebuilding the tree.
- **The guard sits on the append, not on the folded row.** The fold is a trigger on the append, so guarding the append guards every write exactly once and makes an unleased entry unrepresentable. The predicate walks to the root and then looks the Lease up by primary key; joining `lease` against the walk re-runs the recursion per row and costs ten times as much.
- **Leases are symmetric.** Nothing in the API names a holder or tells a person's Lease from an Agent's. `ErrHeld` says a Lease is held and no more.
- **Expiry is the clause `expires_at > now`, never a sweep.** No reader deletes a stale Lease row. Taking over a stale one appends Lease Broken, so a crashed run leaves a trail; there is no Lease Expired.
- **Instants are stored in the fixed-width `stamp` format, not `time.RFC3339Nano`.** RFC3339Nano trims trailing zeros from the fraction, which puts `12:00:00.5Z` before `12:00:00Z` under SQLite's TEXT comparison. `expires_at > now` and `deadline < now` both depend on lexicographic order being chronological order.
- **Reads write nothing.** Overdue is `deadline < now`, a stale Lease is a clause in a predicate, and an Occurrence is computed from its Series. A read that appends anything is a defect with a test against it.
- **Every write carries an Actor; reads are not attributed.** `TODO_ACTOR` names an Agent, and a person falls back to their login. An Agent names itself `<harness>/<model>`, so a history log can say that Opus wrote this and Fable wrote that, and which agent each was acting as. The store neither parses nor validates it: the column is `TEXT` and anything is a legal Actor, because the alternative is a write refused over its own name. A surface splits on the first slash for display and shows what it was given whenever there is none, which is every entry appended before the convention existed.
- **A writing verb takes the Lease covering its target's tree, writes, and gives it back.** A verb acts and exits, so it holds `store.WriteTTL` and never strands a tree behind a dead process. `store.WriteTTL` is the span every surface writes under, so no surface names its own; the breakdown's think-time Lease is the one named exception, below.
- **What a read worked out about a Task is `Task.Marks`.** Overdue, done, declined, deleted and snoozed are decided once in the store and said in the same words everywhere, so a Task cannot read as snoozed from a keyboard and plain on a screen. A surface decides only how to draw them.
- **A column added or renamed after the first release is asked for by name.** `CREATE TABLE IF NOT EXISTS` leaves an existing table as it is and SQLite has no `ADD COLUMN IF NOT EXISTS`, so `addDeclinedAt` and `renameColour` read `pragma_table_info` and alter. Both run inside the schema's own transaction and before the schema, so the trigger bodies reading the column are created after it exists on a store of either age. A rename also needs the folds that read the column to be `DROP` and `CREATE` rather than `IF NOT EXISTS`: SQLite rewrites an existing trigger's body to the new column name but not the payload key it reads, so a stale fold would quietly stop seeing the attribute. The six color folds are pairs for that reason. Entries already in the Change History keep whichever key they were appended with; nothing re-reads them.
- **`Open` retries a busy schema apply.** Turning the write-ahead log on is a `journal_mode` change taking the exclusive lock, and SQLite runs no busy handler for one, so `busy_timeout` cannot cover it: several processes opening a store that does not exist yet leave all but one with `SQLITE_BUSY`. The loser waits only for the winner's switch, so `Open` backs off linearly a few times. Every open after the first finds the log on and the switch a no-op.
- **`Open` applies the schema in one transaction.** Several triggers are a `DROP` followed by a `CREATE`, so an older store gets the current definition; applied without the write lock, two processes opening one store at once interleave those pairs and one fails on a trigger the other has just made.
- **An edit says what it touches and nothing else.** An attribute flag nobody typed leaves its attribute alone; one given empty clears it. The fold reads `json_type(payload, '$.x') IS NULL` for untouched and a JSON null for cleared, which is the distinction `COALESCE` cannot express, and `fs.Visit` is what makes the CLI say it.
- **The lifecycle verbs are one shape.** `complete`, `decline`, `reopen` and `delete` each take one id, no flags, and the same guard, so the dispatch and the CLI's map of them are the only places a new one is named.
- **Exit status is 0 for done, 1 for a failure, 2 for usage, 3 for a refusal.** A refusal is the store turning a write away — no Lease, or one another Actor holds — and a surface distinguishes it from a crash. A bad attribute value is refused where it was typed, so `store.ParseLevel` is the CLI's, not only the write path's.
- **An Attachment is a pointer, and the tracker never holds a copy.** A file path or a web address, written down and nothing more: a path is resolved to an absolute one where it was typed, an address is kept as typed, and nothing is fetched. A target that moves leaves a dead link the tracker cannot tell you about, decided at issue #3, so there is no checker and never will be.
- **Deleting a Task collects nothing.** Nothing was copied in, so there is nothing to collect. The pointers stay on the deleted Task and what they name is untouched.
- **A Series is a rule and nothing else.** Scheduling's two tables hold ids, a rule, a date and a state; no title, description or estimate crosses into it, and `TestNoTaskContentEntersScheduling` reads both tables to check. Tracking points at the rule through `task.series_id`.
- **A rule is written the way it is said, and `schedule.Parse` is the only reader of one.** The units are day, week, month and year, each as `daily`/`weekly`/`monthly`/`yearly` or `every [N] <unit>s`. `on` runs to the next keyword rather than taking one word: a weekly rule names days (`on mon,thu`), a monthly one names either a day of the month (`on 15`) or a weekday counted inside it (`on the third tue`, `on the last fri`, `on the last day`). `Rule.Nth` carries that count with `schedule.Last` for the last one. The counts stop at a fourth, which every month has: a fifth weekday is in some months and not others, so a rule counting one could produce nothing at all and `Next` could not tell that from a rule that has run out. The last one is what a person meant anyway. A yearly rule takes no `on` and steps by twelves of months, so an anchor on the 29th of February clamps to the 28th rather than sliding into March. `String` writes every form back exactly as Parse reads it, because a Series is stored as that text.
- **An Occurrence is computed on every look.** There is no row for a date until somebody ticks, skips or Detaches it, and then it is keyed by (series, date). A reader that shows next year's dates appends nothing and stores nothing.
- **Detaching one date lifts it out into an ordinary Task.** The copy carries the recurring Task's content, deadlined on that date and repeating on nothing, and the rule stops producing the date. Later edits to the rule do not reach it, which is the point of detaching rather than editing the Series.
- **A mark is an ordinary guarded write; changing the rule is too.** Each takes the Lease covering the Task's tree. Creating a Series and pointing the Task at it are one transaction, so a refusal leaves no Series behind.
- **Nothing in Scheduling runs on a schedule.** No sweep materializes dates and nothing is awake to notice one arriving; `src/schedule` says so in its package comment.
- **The charm modules are the `charm.land/...` v2 paths**, not `github.com/charmbracelet/...`. `bubblezone/v2` requires `charm.land/bubbletea/v2`, so mixing the two roots would put two incompatible `tea.Model` types in one program.
- **The TUI's mouse zones come from a per-Model `zone.New()`**, never `zone.NewGlobal()`. `todo serve` runs many sessions in one process, and a global manager would hand one session's hit boxes to another.
- **The v2 View carries the screen and mouse modes.** `Model.View` sets `AltScreen` and `MouseMode`; nothing is toggled through a program option behind the model's back.
- **Everything the keyboard reaches in the main view, the mouse reaches too.** The List dropdown and its options, the sort, every Tag and every footer key are marked zones, and `Model.click` routes a press to whichever one it landed in. A click on a Task puts the cursor on it and a second one on the same Task blows it up, so a Task can be chosen by mouse for a verb without the detail pane opening over the list. A click anywhere with a Task blown up goes back. `bubbles/list` binds keys and not the wheel, so `Model.wheel` turns a notch into a move of the cursor.
- **A footer key and its hit box do the same thing, because they are the same row of the same table.** `taskVerbs` and `viewVerbs` in `src/tui/keys.go` carry the key, the footer's label and the function, and `press`, `click` and `footer` all read them through `do`. `allVerbs` is the two flattened, for the readers answering "what does this key do"; the footer is the only one that wants the rows apart. A verb added there is a key, a hint and a hit box at once, and none of the three can be added without the others.
- **The screen's palette is `src/tui/theme.go` and nothing outside it names a color.** Four roles — accent, muted, faint, danger — as ANSI 256, because the TUI is served over SSH to whatever terminal is on the other end. `formTheme` hands the same four to huh, so every form wears the list's look; `store.Colors` is separate and is what a Task is painted in, deliberately none of the furniture's four.
- **The main view is a header, a pane and a footer, and it fits the terminal exactly.** `View` measures the header and the footer it just drew and gives the rest to the Tasks, so the dropdown opening shortens the pane instead of pushing the footer off the screen. The sidebar is drawn to the pane's height so its rule runs the whole way down. A row is cut to its pane's width by `rowDelegate.render`, because a title or a foot longer than the pane would push the sidebar's rule off the edge of a narrow terminal and smear the frame.
- **The TUI never holds a write transaction across think-time.** A form gathers, `save` writes, and the Lease is taken and released inside that one call. Getting this wrong queues every other writer behind a person staring at a text box, which is why `busy_timeout` is ten seconds and not longer.
- **The TUI hears about other writes by polling the write-ahead log.** `Store.WALToken` is a stat, compared once a second. SQLite cannot push, there is no watcher service, and when the TUI is closed nothing watches because nothing needs to.
- **The keyboard is two rows of keys and there is no palette.** `taskVerbs` is what is done to a Task -- `a` `e` `n` `c` `x` `o` `d` `z` `r` `b` -- and `viewVerbs` what is done to the view: `/` search, `s` sort, `h` hidden, `l` lists, `ctrl+l` and `ctrl+t` for a new List or Tag, `?` ask, `q` quit. The footer draws them in those two rows, wrapped to the terminal's width by `flow`, and a Task verb with nothing under the cursor is drawn faint and does nothing rather than leaving the row. `ctrl+l` and `ctrl+t` are the add and edit screens' own keys for the same popup, so one pair of keys reaches a List anywhere.
- **The Task list is left holding pgup, pgdn, home and end.** `Model.keys` rebinds them off bubbles/list's letter aliases -- b, u, d, f, h, l, g and G -- because those letters are verbs; `/` goes back to the searchbox, which is what a person reaches for to find something. A verb key shadows whatever the list would have done with it, so a key added to either table is a key taken off the list.
- **A color is one of nine, named, and refused anywhere else.** `store.Colors` is the list and `checkColor` gates every write carrying one: a Task's attributes, and a List's or a Tag's creation and rename. The TUI offers them as a select with each name drawn in itself, plus "none", so nothing unpaintable can be typed, and the CLI's `-color` help names the nine. A Task's color paints its title in the main view; the cursor's own style wins on the row under it, so selection stays readable whatever a Task carries.
- **A deadline is typed, and `parseDate` is the one thing on the screen that reads one.** `dateInput` is a validated `huh.NewInput` in the add and edit screens and again in the snooze popup. It takes `2026-01-02`, `2026-01-02 15:04`, and the slashed date a person writes — `4/4/25 9:34 AM`, `04/04/2025 09:34`, either year length, either clock, padded or not — plus any of `store.SnoozeDefaults` by name, which is what "1 week" is. It writes back in `dateLayouts[0]`. The CLI's `parseWhen` is the other reader and takes the ISO layouts only, because a flag is typed once by something that can be told the format.
- **`ctrl+l` and `ctrl+t` describe what is in front of you, and make one when nothing is.** `inFrontOf` is the List the view is narrowed to and the Tag chosen when exactly one is; with none or several the key can only mean "make one". The describe popup carries the name, the color and a Delete confirm, so getting rid of a collection is a tick rather than a key that a slipped finger could hit. Deleting the one the view was narrowed by clears that narrowing. The add and edit screens keep the create-only popup on the same keys: a Task being filed wants a List that does not exist yet.
- **A Subtask is written by hand with `n`, through the same box `a` opens.** `capture.under` is the Task it goes beneath, `draft.parentID` carries it to `save`, and the write is `store.AddSubtask` inside one Lease over the parent's tree, memberships included. The broker's breakdown is the other way to the same call, so a hand-written Subtask and a proposed one are the same entry in the Change History.
- **A snooze is asked for only where there is something to hide.** The add screen has no snooze field: a Task being created is not in anyone's way yet, and `z` is how one gets hidden after that. The edit screen keeps it, so a snooze can be seen and cleared.
- **A form's values live behind a pointer on the Model, never in a field on it.** `Model` is a value, so a form handed `&m.x` writes into the copy that built it and the copy that reads the answer sees nothing. `draft`, `popupDraft`, `breakdown`, `inquiry` and `series` are all pointers for that reason.
- **The write-ahead poll and the resize are read before any screen gets the message.** `tea.Tick` fires once and the chain continues only because `poll` returns the next `watch`, so a tick swallowed by an open form is the last one the process ever sees.
- **Key/value pairs are edited as lines, one `key: value` each.** Nothing offers a widget for a map. The store leaves a key alone unless it is named, so the draft keeps the keys it opened with and names a deleted one as removed rather than leaving it out.
- **`r` is Scheduling's screen**, the counterpart of the verb: the rule, the dates it produces, and `t`, `s`, `e`, `d` to tick, skip, edit or detach the one under the cursor. Each is a guarded write, and every mark re-reads rather than editing what is drawn. Detaching closes the screen, because the date it was open on is an ordinary Task now.
- **Editing one date detaches it, in one store call.** `e` opens the add/edit screen on what the date would become and writes nothing until the form completes, so escaping leaves it an Occurrence and comes back to the Scheduling screen with the date still on it. Saving calls `DetachEdited`, so the detach, the edit and the copy's List and Tag memberships commit together and a refusal leaves no half-detached date behind; the screen closes then, because that date has left the Series. A pointer typed on the way through is the one part outside that transaction, and it goes under the copy's own Lease: the copy is a top-level Task of its own, and the Lease the detach took on it was given back inside the transaction that made it.
- **`store.Detached` is the one statement of what a detached copy carries.** The screen that previews the copy and the append that writes it read the same function, so a preview cannot show a Task the write would not produce. `store.day` builds in `time.Local`, so a detached deadline is the same midnight every other deadline for that day is.
- **The file selector is `bubbles/filepicker`, opened with ctrl+a over the add or edit screen.** What it picks lands on the draft and the form is rebuilt around it, the way creating a List does. A web address cannot be walked to, so the form's Attach line takes one typed.
- **A form names every attribute it showed**, snooze included, so one left empty is cleared. That is the opposite of the CLI's rule, and for the same reason: a surface says what the person saw and left.
- **The main view shows what is in front of you, and the sidebar's states widen it.** The read leaves out snoozed, completed and declined Tasks; `snoozed`, `done` and `declined` are the sidebar's top rows, and choosing one adds those Tasks to what is already in view rather than replacing it, so several can be on at once. `Model.state` is the only reader of the three booleans: it ties each state's name to its field once, and `showing`, `shown` and the read's three `Include` flags all go through it, so the sidebar, the tick and the query cannot come to disagree about which is which. `h` is the snoozed row's key and it has no rivals, because a snooze is looked at and taken off far more often than an ending is. A widened Task comes back carrying its `Marks`, so it says which state brought it.
- **The main view reads and writes nothing, asserted.** `TestTheMainViewWritesNothing` clicks, filters, sorts and expands, then compares `HistoryLength` with what it was.
- **Bare `todo` without a terminal is a usage error**, exit 2, rather than a crash inside the renderer. An Agent that runs `todo` by accident gets a sentence, not a hung process.
- **The sidebar is states, a blank row, then Tags.** A state widens the read and a Tag narrows it, and the blank row between the two blocks is what says so. The Tags are ranked by frequency with variation drawn in: weighted sampling without replacement, so the most-carried Tag usually leads and the list does not read the same every time. Both blocks are hit boxes, `state:<name>` and `tag:<id>`, drawn by the same `pick`.
- **A public key is the only way in, and no allowlist means no server.** `wish.WithAuthorizedKeys` is the whole of the auth, no password handler is registered, and a missing `authorized_keys` is a refusal to listen rather than a door left open.
- **One `tea.Program` per connection, with that session's pty wired to it.** Sessions share the store and nothing else, which is what makes two phones two Actors. A `window-change` arrives as a `tea.WindowSizeMsg`, and a panic is contained to the session it happened on by `recover.Middleware`.
- **A session with no terminal is turned away.** `activeterm` says so; a renderer writing escape codes into a pipe is not an error worth debugging twice.
- **`todo serve` is LAN only, and there is no offline mode.** Reaching it from outside is the homelab's problem, and putting the SQLite file on a network filesystem breaks the write-ahead log, which is one of ADR 0001's re-check triggers rather than something to work around here. A phone with no route to the server has no Tasks.
- **The AI is an outbound HTTP call, never embedded inference.** `inference-runtime-broker` at `10.10.10.13:4010` already runs and is the only thing that infers; `TODO_AI_URL` and `TODO_AI_MODEL` point elsewhere, and with no model named the broker is asked which one it can chat with. That answer is settled once behind a mutex and kept apart from the caller's `Model` field, because a breakdown and an ask both run off the event loop and can be in flight together. A 429 is its memory budget, so it is reported as a wait with a number of seconds rather than as a fault.
- **A breakdown leaves nothing durable unless it is approved.** Proposals are values on a struct: they are shown, ticked or unticked, and gone when the interaction ends. Only submitting writes, and it writes only what is still ticked. There is no Assistance aggregate, no table and no artifact, which is what issue #4 settled.
- **Approval is by position, and a late reply names the interaction that asked.** Two proposals can come back with the same title and a title cannot tell them apart. Escaping does not cancel the call already in flight, so a turn carries the `*breakdown`, `*inquiry` or `*capture` it belongs to and is dropped if that is not the one open.
- **A breakdown leases the whole top-level tree for its duration**, taken before the first call and released when it ends however it ends. That is think-time held on purpose and it is ADR 0002's cost, named there and paid here; a Lease is not a transaction, so nothing else queues behind it.
- **`?` is a read.** The question goes with the Tasks in view, because the broker holds nothing between calls, and no Lease is taken. There is no breakdown verb: approval gates each step, and a verb that acts and exits has nobody to ask.
- **`a` and `e` open one box before they open a form.** Somebody says the Task however they think of it, the broker reads it into the attributes, and the ordinary add or edit form opens filled in for them to correct and submit. Enter is a new line in that box and ctrl+d hands it over, because a dump is paragraphs; an empty box is the way past the broker to the form itself.
- **The box writes nothing and takes no Lease.** The form it opens is the gate, so a dump that is read and then escaped leaves nothing behind, the same as a proposal nobody ticks. That is the opposite of a breakdown, which holds the tree for its duration because it writes per step.
- **A dump amending a Task carries the Task as it stands and comes back whole.** The broker answers with the Task as it should end up, not a difference, because nothing on this side could apply a difference to attributes it was not shown. An answer left empty leaves what was there.
- **What the broker fills in is dropped rather than refused when it cannot be read.** A date, a duration or a level written in a way this program cannot parse is left out of the draft, and a List or Tag name that is not one of the offered ones is dropped rather than created. A name goes out and an id comes back, so the store's rule that a Task carries the id holds through the broker.
- **`todo capture` is the one verb that writes what the broker said, and `-dry` is why it can.** A dump is a person's own words about a Task they are describing, not a proposal of work nobody asked for, so there is nobody left to ask; `-dry` prints what was read and writes nothing, which is where it is checked before it is taken at its word. The Task is written first and its List and Tag membership second under the Task's own Lease, so a refusal there leaves it filed under nothing rather than not written.
- **A `huh` multiselect draws one option unless it is given a height.** `rows` is that height, and every multiselect in this package uses it.
- **`TODO_DB` overrides the store path**, which is how a test and an Agent run against a store of their own. The default sits under the user config directory.

## Work Guidance

- Tests first, at the seams the domain already draws: append-only, purity of reads, the Lease predicate, gaplessness under contention.
- Concurrency claims are asserted against real OS processes, not goroutines. Goroutines share one `*sql.DB` and one pool, so they never reach the file lock the defect hides behind. `TestMain` re-executes the test binary as the child.
- The broker is shared and its chat model is large: a 429 saying `scheduler_busy` means the GPU budget is spoken for, not that anything here is wrong. Tests stand a broker in with `httptest` and never reach the LAN.
- `todo capture` is the dump: words after it are read into one Task, and `-dry` prints what was read without writing.
- `todo attach` is the pointers: bare with an id it lists them, a target adds one, and `-off` takes one off.
- `todo repeat` is the one verb that reaches Scheduling: bare it shows the rule and the next dates, words after the id set the rule, and `-tick`, `-skip`, `-detach` and `-off` are the rest.
- The store's exported vocabulary is `CONTEXT.md`'s: Task, Subtask, List, Tag, Lease, Attachment, Series, Occurrence, Actor.
- A Task's attributes are the set `docs/features.md` asks for and no more: title, description, why, creation date, deadline, estimate, priority, impact, snooze, color, and any number of key/value pairs. Priority and impact are the same three levels, each carrying an example in `PriorityExamples` and `ImpactExamples`. The four offered snoozes are 1 hour, 1 day, 1 week, 1 month, and the month one clamps to the target month's last day.
